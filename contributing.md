# 🛠️ Contributor's Guide: Extending the RECIPE Engine

Thank you for contributing to the RECIPE framework. This project maintains a **500k LoC architecture** where safety, performance, and deterministic behavior are the highest priorities. 

Please follow these guidelines when adding new parsers or modifying the core lensing logic.

---

## 🏗️ The Golden Rule: Macros First
We avoid manual implementation of the `IngredientParser` trait for standard types. To ensure boundary checks and endianness logic are applied consistently, always use the provided macro factory.

### 1. Adding a New Scalar Parser
If you are adding a new numeric or primitive type, use the `impl_simple_parser!` macro. 

```rust
// Example: Adding a specialized 128-bit unsigned integer
#[cfg(feature = "extra_large")]
impl_simple_parser!(U128Parser, U128, u128, 16);
```

### 2. Adding a Fixed-Array Parser
For types that are always a specific byte-width (like UUIDs or specialized hashes), use `impl_fixed_array_parser!`.

```rust
// Example: Adding a 16-byte UUID parser
impl_fixed_array_parser!(UuidParser, Uuid, [u8; 16], 16);
```

---

## 🛡️ Safety Requirements
Any manual implementation of a parser **must** adhere to these three invariants:

### A. Jurisdictional Integrity
Never access `data` slices directly using hardcoded indices. Always use `calculate_bounds` to resolve the start and end coordinates. This ensures that the `max_length` safety ceiling is respected.



### B. UTF-8 Resilience
If your parser handles text, it **must** use `from_utf8_lossy`. We do not allow parsers to panic or fail the entire ingestion pipeline due to a single malformed character.

### C. Endian Neutrality
If the data is multi-byte, the parser must respect the `Endianness` flag in the `Ingredient` blueprint. Use the `from_be_bytes` and `from_le_bytes` patterns generated by our numeric macros.



---

## 🧪 Testing Standards
No parser will be merged without an accompanying test suite in the `tests` module. Your tests must cover:
1.  **Success Path**: Valid data reconstruction.
2.  **Endianness**: Verification of both BE and LE inputs.
3.  **Boundary Failure**: Passing a slice that is too small (should return `RecipeError::OutOfBounds`).
4.  **Length Mismatch**: Passing an `Ingredient` with a length that doesn't match the physical type requirements.

---

## 🚦 Feature Gating
We keep the core engine lean. If your parser introduces a new dependency or handles a specialized domain (like `cryptography` or `advanced_networking`), it must be gated behind a Cargo feature.

```rust
#[cfg(feature = "my_new_feature")]
pub struct MyNewParser;
```

---

## 🔄 The Pull Request Process
1. **Branching**: Create a feature branch from `main`.
2. **Linting**: Run `cargo fmt` and `cargo clippy`. Clippy warnings are treated as errors.
3. **Documentation**: Update the `README.md` if you add a new top-level feature or parser category.
4. **Review**: All PRs require a sign-off from a Staff Engineer familiar with the Memory Lensing logic.

---

> **Note on Performance**: Avoid heap allocations inside the `parse()` loop whenever possible. If you must allocate (e.g., `Vec` or `String`), ensure the `Ingredient` has a reasonable `max_length` set to prevent memory exhaustion attacks.
